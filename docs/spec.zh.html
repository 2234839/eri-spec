1. 定义

ERI（Embedded Result Interface，嵌入式结果界面）是一种让 Agent 输出变为可交互的规范。Agent 处理用户请求后，输出嵌入式 UI（iframe）而非纯文本——只需一个 skill.md 和一个 URL。

角色职责
Agent理解意图、调用 API、构造嵌入 URL、输出 UI
提供者编写 skill.md 并提供一个 HTTPS 嵌入页面（见最小示例）
平台渲染 iframe（大多数已支持）

快照式输出——Agent 不监听已输出的界面，每次新指令生成全新嵌入（见第 3 节）。第三方应用独立运行——只需提供一个 HTTPS 页面。

符合性——满足以下条件即达到 ERI Level 1 合规：（1）提供者提供从 URL 参数读取初始状态的 HTTPS 嵌入页面；（2）Agent 遵循四步工作流；（3）平台以 sandbox="allow-scripts" 渲染 iframe。无需注册，无需认证。

2. 工作流

1. 理解意图提取参数
→
2. 调用 API获取结构数据
→
3. 构造 URL编码参数
→
4. 输出 UIiframe / 纯文本

步骤 1 和 3 是 Agent 本身就会做的事。剩余两步涉及外部系统：

调用 API Agent — Agent 从服务端调用第三方应用的 API（不是从用户浏览器）。标准 HTTP，结构化 JSON。无需配置 CORS。

POST /api/calculate
Body: {"expr": "99.5 * 3"}
Response: {"expr": "99.5 * 3", "result": 298.5}

输出 UI Agent 平台 — Agent 输出 iframe。大多数 Web Agent UI 会自动添加 sandbox 属性渲染 iframe。不支持的平台降级为纯文本。

<iframe src="https://app.example.com/embed#encoded_data" width="100%" height="400"></iframe>

3. 对话流程

iframe 内的编辑不会通知 Agent。每轮新对话：

  1. Agent 从上下文中读取上一次的结果
  2. 结合新输入，重新调用 API
  3. 输出全新的嵌入界面（旧界面不更新）

上下文来自 Agent 平台的对话历史——Agent 能看到自己之前的文字输出（包括 API 结果）。无需额外的状态机制。

用户: "帮我算 3 件商品，每件 99.5 元"
Agent: 调用 API → 输出 iframe 显示 99.5 * 3 = 298.5

（用户在 iframe 中修改数值，Agent 不感知）

用户: "再加上 8% 的税"
Agent: 读取上下文（上次结果：298.5），调用 API 传入 298.5 * 1.08
       → 输出新 iframe 显示 298.5 * 1.08 = 322.38

4. Skill 编写 提供者

skill.md 放在 Agent 能发现的位置——可以是自定义指令、GPT Action、Claude 技能文件，或平台提供的任何 Agent 行为定义机制。格式在所有平台上都一样。

一个最小化的 ERI Skill：

---
name: 工具名称
description: 工具描述
---
## 工作流
1. 从用户输入中提取参数
2. 调用 API：POST https://api.example.com/calculate
   Body: {"expr": "表达式"}
3. 将 API 响应编码到 URL hash 中
4. 输出为 iframe：https://app.example.com/embed#<编码后的响应>
   （平台无法渲染时降级为纯文本）

Agent 读取这个工作流，执行每一步，输出 iframe。

Frontmatter（name、description）遵循标准 YAML 约定。正文标题（## Workflow、## 工作流 或任意标题）及其内容都是自由格式——用 Agent 能理解的自然语言编写即可。格式为纯 Markdown。

完整示例：NoteCalc（真实实现） · 模板（复制后填入自己的内容）。

5. 嵌入式页面要求 提供者

要求说明
HTTPS必须使用 HTTPS
URL 参数读取从 URL hash 中读取初始状态（推荐），或使用 query 参数。编码：encodeURIComponent(JSON.stringify(data))
自包含所有交互自行处理。不依赖宿主 JS/CSS。响应式布局。
postMessage （可选）iframe 内变化可通过 postMessage 通知宿主
主题适配 （可选）读取 URL 参数或宿主颜色方案适配明暗主题

最小嵌入页面示例

Agent 在服务端调用 API，通过 URL hash 将结果传递给嵌入页面。页面只负责渲染——iframe 内无需任何计算逻辑。

<!DOCTYPE html>
<html>
<body>
<div id="out" style="font-size:24px"></div>
<script>
  /** Agent 通过 hash 传入 JSON: {"expr":"99.5*3","result":298.5} */
  const data = JSON.parse(
    decodeURIComponent(location.hash.slice(1))
  );
  document.getElementById('out').textContent =
    data.expr + ' = ' + data.result;
</script>
</body>
</html>

此最小示例仅渲染结果。生产级嵌入页面还需添加响应式布局、输入验证、错误状态和主题适配。

6. 安全

角色规则
平台为 iframe 添加 sandbox="allow-scripts"。仅在嵌入页面需要自身 cookie/storage 时才添加 allow-same-origin（注意：此组合实际上取消了沙箱限制）。不得将用户凭证传递给第三方 iframe。
提供者不依赖 document.cookie（沙箱环境可能不可用）。不使用 window.opener 或 window.top 做导航/DOM 访问（Level 2 的 window.parent.postMessage 是安全的）。所有输入做 XSS 防护。绝不在 URL hash/query 参数中放置 PII 或敏感数据——URL 会被记录在浏览器历史、代理日志和 Referrer 头中。对于敏感数据，应在 URL 中传递短期令牌，由嵌入页面通过 API 调用获取实际数据。

7. 渐进等级

等级能力谁需要做什么
0纯文本输出Agent 即可——不需要其他任何配合
1iframe 嵌入提供者 嵌入页面 + 平台 iframe 支持（大多数平台已有）
2双向通信Level 1 + 提供者 平台 双方实现 postMessage

Level 2 适用于平台需要对 iframe 内的用户编辑做出响应的场景（如自动保存、实时预览）。使用 postMessage 并指定具体 origin——绝不使用 "*"：

// iframe → Agent 平台：通知用户修改了某个值
window.parent.postMessage({
  type: "eri:valueChanged",  // 必须以 "eri:" 开头
  path: "items.price",       // 所修改字段的点分路径
  value: 199                 // 新值
}, "https://agent-platform.example.com");

// 接收方必须验证 origin：
// window.addEventListener("message", e => {
//   if (e.origin !== "https://your-app.example.com") return;
//   ...
// });

// Agent 平台 → iframe：向嵌入页面推送更新数据
iframe.contentWindow.postMessage({
  type: "eri:update",
  data: { items: [...], total: 597 }
}, "https://your-app.example.com");

8. 适用场景

适合——任何用户想要微调 Agent 输出的场景：

场景嵌入页面做什么
计算器 / 电子表格渲染表达式和结果；用户直接编辑数值
图表 / 仪表盘渲染可视化；用户调整筛选条件或日期范围
表单 / 问卷构建器渲染预览；用户重排字段或修改选项
文档编辑器渲染格式化内容；用户调整排版或字体
设计工具渲染预览；用户调整颜色、间距或尺寸
代码演练场渲染带语法高亮的代码；用户编辑并查看输出

不适合：纯信息查询（不需要交互）、长文本生成、实时同步（ERI 是快照式的）。

9. 局限性

  • 快照式输出——每轮对话产生全新的嵌入，Agent 无法观察 iframe 内的编辑。完整流程见第 3 节，Level 2 postMessage 双向同步见第 7 节。
  • 设备能力受限——沙箱 iframe 对设备 API（GPS、摄像头等）的访问受限。仅支持标准 Web 能力。
  • URL 大小限制——编码到 URL hash 中的状态受浏览器 URL 长度限制（安全范围约 2KB，上限约 8KB）。数据量较大时，应在嵌入页面内通过 API 调用获取数据。

10. 错误处理

故障Agent 行为
API 返回错误或超时以纯文本报告错误。不嵌入包含错误状态的 iframe。
嵌入 URL 不可达输出纯文本降级。用户仍然获得 API 结果。
平台阻止 iframe降级为纯文本——Agent 的文字输出仍然可见。
URL 编码数据超出限制提供者应设计嵌入页面接受短期令牌，并通过服务端 API 获取数据。

ERI 的纯文本降级不是缺陷——它是基线。每个 ERI 输出都应包含文本摘要，确保用户无论 iframe 是否渲染都能获得价值。

11. 行业格局

交互式 Agent 输出存在三种方案：

ERIMCP AppsA2UI (Google)
方式通过 URL 嵌入沙箱小应用Agent 以 JSON 声明 UI
平台要求渲染 iframe（已有）MCP 运行时A2UI 渲染器
今天可用所有平台仅 MCP 平台仅 A2UI 平台
丰富能力仅标准 Web平台 API、实时通信原生渲染

MCP Apps 和 A2UI 提供更丰富的能力——原生 API、实时同步、平台集成。ERI 用这些能力换取了今天的通用可用性。随着 MCP 和 A2UI 的采用增长，ERI 的"处处可用"优势会收窄——但其简洁性不会：一个嵌入页面，无需平台特定的打包。从 ERI 开始，等目标平台支持更丰富的协议时再升级。

ERI 相比普通 iframe 增加了什么：ERI 定义了一个可复用、跨平台的模式——skill.md 指导 Agent 调用特定 API、编码结果、嵌入特定 URL，并提供纯文本降级。没有这个约定，每个 Agent-提供者集成都是临时拼凑。ERI 使其一致且可发现。
