ERI 规范 — Embedded Result Interface

版本：1.0  |  状态：Stable  |  许可：MIT

1. 定义

ERI（Embedded Result Interface，嵌入式结果界面）是一种 Skill 编写模式。Agent 处理用户请求后，输出一个可交互的嵌入式 UI（iframe），而不是（或不仅是）纯文本。

ERI 中谁做什么：

  • Agent 理解意图、调用 API、构造嵌入 URL、输出 UI——这是任何 AI Agent 已有的能力（读取 skill、调用 API、输出文本）。不需要平台改动。
  • 提供者 编写 skill.md 并提供一个 HTTPS 嵌入页面——这是第三方应用唯一需要做的事。约 40 行代码。
  • 平台 需要在渲染 iframe 时配合——大多数平台已经支持 iframe。纯文本兜底完全不需要平台支持。

核心约束：

  • 无新协议、无新字段——仅通过 skill.md 中的约定写法实现
  • 快照式输出——Agent 不监听已输出的界面，每次新指令生成全新界面（见第 3 节）
  • 第三方应用独立运行——只需提供一个 HTTPS 页面

2. 工作流

1. 理解意图提取参数
→
2. 调用 API获取结构数据
→
3. 构造 URL编码参数
→
4. 输出 UIiframe / 纯文本

步骤 1 和 3 是 Agent 的天然能力——从用户输入中提取意图，按模板拼接 URL。涉及外部系统的两个步骤是：

2.1 调用 API Agent

Agent 调用第三方应用的 API 获取结果。标准 HTTP，结构化 JSON。

POST /api/calculate
Body: {"content": "99.5 * 3"}
Response: {"result": 298.5}

2.2 输出 UI Agent 平台

<iframe src="https://app.example.com/embed#encoded_data" width="100%" height="400"></iframe>

安全属性（sandbox 等）由 Agent 平台自动添加。如果平台无法渲染 iframe，则降级为纯文本输出。

3. 对话流程

用户在嵌入式界面上的修改不会自动通知 Agent。当用户发起新一轮对话时：

  1. Agent 从对话上下文中读取上一次的结果
  2. 结合新输入，重新调用 API
  3. 输出全新的嵌入式界面（不更新旧界面）
用户: "帮我算 3 件商品，每件 99.5 元"
Agent: [输出 iframe: 99.5 * 3 = 298.5]

（用户在 iframe 中修改数值，Agent 不感知）

用户: "再加上 8% 的税"
Agent: 读取上下文 last_result=298.5，计算 298.5 * 1.08
       [输出新 iframe: 298.5 * 1.08 = 322.38]

4. Skill 编写 提供者

一个最小化的 ERI Skill（skill.md）：

---
name: 工具名称
description: 工具描述
---
## 工作流
1. 从用户输入中提取参数
2. 调用 API：POST https://api.example.com/calculate
   Body: {"expr": "表达式"}
3. 构造嵌入 URL：https://app.example.com/embed#URLEncoded(expr)
4. 输出 UI（优先级：iframe > 纯文本）

Agent 读取这个工作流，执行每一步，输出 iframe。

5. 嵌入式页面要求 提供者

要求说明
HTTPS必须使用 HTTPS
URL 参数读取能从 URL hash / query 中读取初始状态
自包含页面内所有交互自行处理，不依赖宿主
响应式适应不同宽度的嵌入容器
无外部依赖不依赖宿主页面的 JS/CSS
postMessage （可选）iframe 内变化可通过 postMessage 通知宿主
主题适配 （可选）读取 URL 参数或宿主颜色方案适配明暗主题

最小嵌入页面示例

<!DOCTYPE html>
<html>
<body>
<input id="expr" style="width:100%;font-size:18px">
<div id="result" style="font-size:24px;margin-top:8px"></div>
<script>
  const expr = decodeURIComponent(location.hash.slice(1));
  document.getElementById('expr').value = expr;
  function update() {
    const v = document.getElementById('expr').value;
    try { document.getElementById('result').textContent = eval(v); }
    catch(e) { document.getElementById('result').textContent = ''; }
  }
  document.getElementById('expr').oninput = update;
  update();
</script>
</body>
</html>

20 行代码。从 URL hash 读取、自包含、即时交互。部署到任意 HTTPS 主机即可获得一个可用的 ERI 嵌入页面。

6. 安全

Agent 平台侧 平台

  • iframe 必须添加 sandbox 属性限制权限
  • 建议添加 sandbox="allow-scripts allow-same-origin"
  • 不应将用户凭证传递给第三方 iframe

第三方应用侧 提供者

  • 不依赖 document.cookie（沙箱环境可能不可用）
  • 不使用 window.opener 或 window.top
  • 所有输入做 XSS 防护

7. 渐进等级

等级能力谁需要做什么
0纯文本输出Agent 即可——不需要其他任何配合
1iframe 嵌入提供者 嵌入页面 + 平台 iframe 支持（大多数平台已有）
2双向通信Level 1 + 提供者 平台 双方实现 postMessage

Level 0 是基线——一个返回文字结果的 skill.md。Level 1 才是 ERI 的起点：同样的工作流，但 Agent 嵌入可交互的 iframe，而不仅是文字。

Level 2 的 postMessage 协议（使用具体 origin，不要用 "*"）：

// iframe → Agent 平台
window.parent.postMessage({
  type: "eri:valueChanged",
  path: "field.path",
  value: newValue
}, "https://agent-platform.example.com");

// Agent 平台 → iframe（可选）
iframe.contentWindow.postMessage({
  type: "eri:update",
  data: { ... }
}, "https://your-app.example.com");

8. 适用场景

适合：计算工具、表单/问卷、数据可视化、文档编辑、设计工具、代码编辑器——任何用户想要微调 Agent 输出的场景。

不适合：纯信息查询（不需要交互）、长文本生成、实时同步（ERI 是快照式的）。

9. 行业格局

交互式 Agent 输出存在三种方案：

  • ERI — 通过 URL 嵌入任何 Web 应用。在所有平台上都能用。你控制 UI。
  • MCP Apps（Anthropic & OpenAI）— MCP 生态中的沙箱小应用。仅在支持 MCP 的平台上可用。
  • A2UI（Google）— Agent 以 JSON 声明 UI，客户端原生渲染。仅在支持 A2UI 的平台上可用。

ERI 不与 MCP Apps 或 A2UI 对立——它是入口。作为第三方提供者，ERI 让你以最小代价获得最广覆盖。今天嵌入，等平台支持更丰富的协议时再升级。
