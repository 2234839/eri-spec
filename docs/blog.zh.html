超越文字：为什么 AI Agent 需要交互式 UI

发布日期：2026-05-15

文字陷阱

每个主流 AI Agent——ChatGPT、Claude、Gemini——都有同样的输出局限。你让它算个东西，它回复：

99.5 × 3 = 298.5

对的。但你想看 4 件是多少。或者 5 件。或者加 8% 的税。每次变化都意味着又一轮对话——描述想改什么，等回复，再描述下一个。

问题不是准确性。问题是媒介。不只是计算——图表需要可调的坐标轴，表单需要可编辑的字段，配色需要可拖动的滑块。每次 Agent 都把你逼回文字。

生态解决了输入（MCP、Function Calling、REST），没解决输出。

引入 ERI

ERI（嵌入式结果界面）让你的 Web 应用以实时可编辑的 UI 出现在任何 Agent 对话中——ChatGPT、Claude、Gemini。用户直接交互——无需等待 Agent 来回。

你写一个 skill.md，告诉 Agent 如何调用你的 API、嵌入哪个 URL。见规范中的最小示例，或直接使用可复制模板。

从零到可运行嵌入，不到一天——NoteCalc 参考实现中，skill.md 约十分钟，嵌入页面一个下午。现在试试。

你当然可以直接嵌入 iframe

没错。你可以直接告诉 Agent "嵌入这个 URL"，它会生成一个 iframe。那为什么还需要一个规范？

因为没有一个约定，每次 Agent-提供者的集成都是临时拼凑。一个 Agent 把数据放在 hash 里嵌入你的 URL。另一个放在 query 参数里。第三个忘了在不支持 iframe 的平台提供纯文本降级。你的 API 每次被不同的方式调用，嵌入页面没有一个一致的契约。

ERI 定义了这个契约：skill.md 指导 Agent 调用特定 API、编码结果、嵌入特定 URL、并包含纯文本降级。同样的模式，每个 Agent，每个平台。嵌入页面有清晰的规范可以遵循。结果是一致且可复用的——不是一次碰巧。

为什么先选 ERI

今天就上线，以后再升级。ERI 利用平台已有的能力——iframe 渲染——所以今天大多数平台都能用。等目标平台支持 MCP Apps 或 A2UI，你的嵌入页面可以直接沿用——它构成打包给更丰富协议的核心。你在构建资产，不是一次性原型。

一次实现，所有平台。ChatGPT、Claude、Gemini 都在 Agent 输出中渲染 iframe（已在 GPT-4o、Claude 3.5+、Gemini 2.0+ 上验证，2026 年 5 月）。一个嵌入页面 + 一个 skill.md 覆盖三个平台。无需逐平台 SDK，无需平台审批流程，无需供应商特定的打包。

零协议承诺。你的嵌入页面是独立的 HTTPS 应用——ERI 不是运行时依赖。当你准备好接入 MCP Apps 时，将它包装在 manifest 中，通过 MCP 运行时暴露同一个页面。同样的 UI、同样的 API，额外的平台能力。投入会持续累积。

代价：快照式输出（每轮用户对话产生全新嵌入），无原生设备 API，URL 大小限制。详见规范局限性和大数据集模式。
