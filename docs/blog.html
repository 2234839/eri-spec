Beyond Text: Why AI Agents Need Interactive UI

Published: 2026-05-15

The Text Trap

Every AI Agent has the same problem. You ask it to calculate something, and it responds with:

99.5 × 3 = 298.5

Correct. But now you want to see 4 items. Or 5. Or with 8% tax. Each variation means another round of conversation — describe what changed, wait for a response, describe the next change.

The problem isn't accuracy. The problem is the medium. Not just calculations — charts need adjustable axes, forms need editable fields, color palettes need draggable sliders. Every time, the Agent forces you back into text.

The ecosystem has solved input. It hasn't solved output.

Enter ERI

ERI (Embedded Result Interface) lets your web app appear as a live, editable UI inside any Agent conversation — ChatGPT, Claude, Gemini. The user interacts directly — no Agent round trips needed.

You write a skill.md telling the Agent how to call your API and which URL to embed. See the spec for a minimal example, or grab the copy-paste template.

Under a day from zero to working embed. Try it now.

Yes, You Can Already Embed an Iframe

Right. You can tell an Agent "embed this URL" and it will produce an iframe. So why a spec?

Because without a convention, every Agent-provider integration is ad-hoc. One Agent embeds your URL with the data in the hash. Another puts it in query params. A third forgets to include a text fallback for platforms that strip iframes. Your API gets called differently each time, and your embed page has no consistent contract.

ERI defines the contract: a skill.md instructs the Agent to call a specific API, encode the result, embed a specific URL, and include a plain text fallback. Same pattern, every Agent, every platform. The embed page has a clear spec to build against. The result is consistent and discoverable — not a lucky coincidence.

Three Paths to Interactive Agent Output

The industry is converging on the same problem from three directions:

ERI — embed your web app via URL. Works on every platform today because it uses iframes. You build an HTTPS page, write a skill.md, and ship. The trade-off: full web platform (HTML/CSS/JS/Canvas/WebGL), but no native device APIs or real-time sync.

MCP Apps (Anthropic / OpenAI) — sandboxed mini-apps with platform APIs and real-time communication. Richer capabilities, but only on MCP-enabled platforms. Requires packaging in a platform-specific format.

A2UI (Google) — the Agent declares UI as JSON, and a platform renderer turns it into native controls. Native rendering quality, but requires an A2UI renderer that most platforms don't have yet.

Why ERI First

Ship today, upgrade later. ERI works on most platforms today because it uses what platforms already have: iframe rendering. When your target platforms support MCP Apps or A2UI, your embed page carries forward — it becomes the core you package for those protocols. You're building an asset, not a throwaway prototype.

One implementation, all platforms. ChatGPT, Claude, and Gemini all render iframes in Agent output. One embed page + one skill.md reaches all three. No per-platform SDK, no platform approval cycle, no vendor-specific packaging.

Zero protocol commitment. ERI is not a runtime dependency. Your embed page runs independently — it's a regular HTTPS page. If you decide to migrate to MCP Apps or A2UI, the embed page doesn't change. You add a packaging layer on top.

Migration path: Your ERI embed page is already an HTTPS web app. When MCP Apps arrive, you wrap it in a manifest and expose the same page through the MCP runtime. Same UI, same API, additional platform capabilities. The investment compounds.

Trade-offs: snapshot-based output (each user turn produces a fresh embed), no native device APIs, URL size limits for encoded data. See spec limitations and large data pattern for mitigations.
